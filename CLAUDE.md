Env vars: copy `.env.example` to `.env` and fill in a Supabase project's URL/anon key (`EXPO_PUBLIC_`-prefixed, inlined by Metro at build time — see `lib/supabase.ts`, which throws at import time if they're missing). The Anthropic key is a **Supabase secret**, not an app env var — it's only ever read inside `supabase/functions/*/index.ts` (Deno), never bundled into the client.

Database: schema lives only in `db/migrations/*.sql`, applied in filename order via the Supabase SQL Editor (or `supabase db push` with the CLI). There is no ORM — the Supabase dashboard is never the source of truth; if the schema changes, write a new numbered migration and update `types/database.ts` to match.

## Architecture

**Routing (expo-router, file-based):** `app/_layout.tsx` wraps the whole tree in `AuthProvider` > `InventoryProvider` (moved to the root in Phase 3 so `sous-chef.tsx` and `recipe/[id].tsx` — both outside `(tabs)` — can read inventory too; it's a no-op until there's a session) and mounts a root `Stack` with seven screens: `(auth)`, `(tabs)`, `sous-chef` (modal), `recipe/[id]`, `recipe/[id]/cook`, `recipe/[id]/finish`, `check-in` (modal). Route groups don't add URL segments, so exactly one `index.tsx` across `(auth)`/`(tabs)` may claim `/` — `(tabs)/index.tsx` owns it; `(auth)` has no `index.tsx` on purpose (see git history for why: both groups having an index route collides on `/`). The auth gate isn't a redirect at the root — each group's own `_layout.tsx` checks `useAuth().session` and calls `<Redirect>` to the other group. `(tabs)/pantry/` is its own nested `Stack` (list → add → `[id]` edit → quick-add → receipt-scan → quick-add-review, the last shared by both add flows). `app/recipe/[id].tsx` (a file) and `app/recipe/[id]/` (a directory holding `cook.tsx`/`finish.tsx`) coexist fine as siblings under the same dynamic segment name — verified via `expo export --platform web`, no route-conflict error.

**State:** two React contexts, not a global store. `lib/auth/AuthContext.tsx` wraps Supabase auth session state. `lib/inventory/InventoryContext.tsx` wraps inventory items, canonical foods, and `food_storage_rules` for the whole authenticated app, and also carries `quickAddDraft` — the parsed-but-unsaved batch from either Quick Add or Receipt Scan (each `QuickAddDraftItem` carries its own `source`) — so the two entry screens → `quick-add-review.tsx` handoff doesn't need to serialize items through router params.

**Supabase typing gotcha:** `types/database.ts`'s `Database` type must use `type X = {...}` (type aliases), never `interface X {...}`, for every `Row`/`Insert`/`Update` shape. `@supabase/supabase-js`'s generics require each table to structurally satisfy `Record<string, unknown>`-style index signatures, and TypeScript only allows that implicit match for type aliases, not named interfaces — using an interface silently degrades every `.from(...)` call to `never`. Each table also needs a `Relationships: []` field and the schema needs `Views`/`Functions`/`Enums`/`CompositeTypes`, matching what `supabase gen types typescript` would produce.

**Quick Add / Receipt Scan normalization pipeline (Phase 2):** `lib/quickAddParser.ts` no longer parses anything itself — it calls the `quick-add-parse` Edge Function (`supabase/functions/quick-add-parse/`) and maps the response. `lib/receiptScanner.ts` does the same via `receipt-scan`, after normalizing the photo to JPEG (`expo-image-manipulator` — Claude's vision API rejects HEIC, the iOS camera default) and uploading it to the private `receipts` Storage bucket. Both Edge Functions share one normalization contract in `supabase/functions/_shared/matching.ts` (the canonical-foods prompt fragment + JSON response validator) — that shared module, not a literal two-call pipeline, is what "reuse the normalization pipeline" means here; each function still makes just one Claude call. Neither function ever writes to `inventory_items` — both only return suggestions, and every result still lands on `quick-add-review.tsx` before saving. `lib/functionsError.ts` unwraps the real error message from a `FunctionsHttpError`, shared by both client modules.

**Deterministic expiry (Phase 2, no LLM):** `db/migrations/0006_expiry_estimation.sql` installs a Postgres trigger that looks up `food_storage_rules` (seeded in `0005_food_storage_rules.sql`, keyed by `canonical_food_id` + `preparation_state` + `storage_location` + `is_opened`) and sets `expiry_estimated` whenever those fields or `purchased_at`/`opened_at` change. No match (unresolved `canonical_food_id`, or a combination with no seeded rule) means `expiry_estimated` stays null — never a guessed number. The client mirrors this same lookup in `lib/foodStorageRules.ts`'s `findStorageRule` to read `is_safety_critical` for display tone (see the edit screen). `lib/formatInventory.ts`'s `getEffectiveExpiry` prefers `expiry_user_provided` over `expiry_estimated`.

**Uncertainty rule (cross-cutting):** any inventory data not confirmed by the user must be visually distinguishable everywhere it's shown. This is enforced by a single component, `components/UncertaintyBadge.tsx`, rendered whenever `verification_status` is `ai_estimated` or `needs_verification` (see `lib/formatInventory.ts`'s `isUncertain`). Don't build a second/parallel way to flag uncertain data — route new cases through this component and status field. Saving from the edit screen, or tapping a row's quick-verify checkmark (`InventoryItemRow`'s `onVerify`), is what clears it — both set `verification_status: 'confirmed'` and `last_verified_at`.

**Rescue Row (Phase 2):** `lib/rescueRow.ts`'s `getRescueRowEntries` is a pure function over already-loaded `items` — no query, no LLM. It classifies each item by at most one reason (expiring > leftover > low quantity, in that priority order) and sorts soonest-first. Keep it that way — this is explicitly "what needs attention," not recommendation logic.

**Recipe-to-inventory matching (Phase 3):** `lib/recipeMatching.ts`'s `matchRecipeToInventory`/`matchIngredient` is the deterministic, non-LLM classifier (Already Have / Verify / Missing) reused everywhere a recipe renders — `RecipeCard`, the recipe detail screen, and both server-side generation paths. It has an independent Deno port at `supabase/functions/_shared/recipeMatching.ts` (same algorithm, same unit-synonym table as `lib/quickAddParser.ts`'s `UNIT_WORDS`, kept in sync manually — there's no cross-runtime import here, same reasoning as the Supabase-client duplication below). The recipe detail screen (`app/recipe/[id].tsx`) deliberately re-runs this live against current `useInventory().items` rather than trusting `recipes.ingredients[].inventory_match`, which is only a point-in-time snapshot for explainability.

**Sous Chef & recipe generation (Phase 3):** `supabase/functions/sous-chef-chat/` runs a real manual Claude tool-calling loop (six tools: `get_inventory`, `get_rescue_items`, `get_user_preferences`, `generate_recipe`, `match_recipe_to_inventory`, `create_shopping_items` — a no-op stub) — the model decides when to call what; it never fabricates inventory data because every fact it uses comes back from a real tool call. Each chat turn is stateless: the client (`app/sous-chef.tsx` via `lib/sousChef.ts`) resends the full text-only history, and the server re-gathers fresh context every turn rather than replaying old tool_use/tool_result blocks. `supabase/functions/recipe-suggestions/` is the non-conversational sibling for Home's suggestions — same generation/matching pipeline, invoked directly instead of via a tool loop. Both share `_shared/recipeGeneration.ts` (one Claude call per generation batch — extraction and canonical-food matching happen together in one prompt, same "shared module over literal two-call pipeline" design as Phase 2's normalization) and `_shared/recipePayload.ts` (shapes a generated+matched recipe into the wire format both entry points return, so the client's `RecipeCard` never sees two different shapes).

**Dietary restrictions are a hard constraint, structurally enforced — not just prompted.** `_shared/dietaryRestrictions.ts`'s `findDietaryViolations` runs a keyword check against every candidate recipe's ingredient names; `generateRecipes` in `_shared/recipeGeneration.ts` discards any violating recipe and regenerates (up to 3 attempts) before anything reaches the client. If you touch recipe generation, do not remove or bypass this check even if it seems redundant with the system prompt — the system prompt is the soft layer, this is the hard one. The keyword list is a curated common set (vegetarian/vegan/pescatarian/gluten-free/dairy-free/nut-free/shellfish-free/egg-free), not exhaustive — see README's Known limitations before treating it as a real allergen safety system.

**Recipes persist, and now they cook (Phase 4).** `recipes` (`db/migrations/0008_recipes.sql`) stores what's generated; tapping a `RecipeCard` (in chat or on Home) saves it via `lib/api/recipes.ts`'s `suggestionToRecipeInsert` + `createRecipe`, then navigates to `recipe/[id].tsx`. Its "Cook This" button pushes `recipe/[id]/cook` (step-by-step, per-step timers via `lib/parseStepDuration.ts`'s regex, inline ingredients via `lib/matchIngredientsToStep.ts`'s substring match, a `TechniqueVideoSlot` placeholder for Phase 7). "Finish Cooking" from any step pushes `recipe/[id]/finish`.

**The confirm-before-mutate rule is the load-bearing one for Phase 4 (and the whole app's trust model).** `recipe/[id]/finish.tsx` is the *only* place recipe-related code writes to `inventory_items` — verified by grepping every `editItem`/`removeItem`/`addItem` call site (see Commands) and confirming the only hits outside Pantry's own pre-existing CRUD screens are inside `finish.tsx`, gated behind the user's "Update Pantry" tap. `lib/cookingMutations.ts`'s `proposeInventoryMutations` is deterministic (no LLM) and only *proposes* — it returns editable `ProposedMutation[]`, it never calls `editItem`/`removeItem` itself. Re-run that grep after touching anything recipe- or cooking-related; a new hit outside `finish.tsx` (behind confirmation) or Pantry is a bug, not a feature.

**Mutation modes (`lib/cookingMutations.ts`):** `'quantity'` (both the recipe ingredient and a matched item have a numeric quantity in a comparable unit — reuses `lib/recipeMatching.ts`'s exported `normalizeUnit`) scales the deduction by `servingsPrepared / recipe.servings` and spreads it across matched items in order; fully-consumed precise quantities are removed (`removeItem`), not left at zero. `'state'` (only an approximate `quantity_state` match) steps down one level via a fixed `STATE_STEP_DOWN` map, floored at `almost_empty` — never auto-removed, per spec's "leave it at Almost Empty" default. An ingredient with no canonical match, or a match with neither a comparable quantity nor a `quantity_state`, produces no proposal at all — there's nothing responsible to change automatically.

**Leftovers close the loop back into Rescue Row.** Confirming the leftovers prompt in `finish.tsx` calls `addItem` with `preparation_state: 'leftover'`, `source: 'cooking'` (a value added to the `inventory_source` enum in its own migration, `0011_inventory_source_cooking.sql` — Postgres won't let a new enum value be used in the same transaction that adds it), `storage_location: 'fridge'`, `verification_status: 'confirmed'` (the user just made it, no uncertainty). No changes needed to `lib/rescueRow.ts` — it already ages any `leftover` item by `opened_at ?? created_at`, and a freshly created leftover naturally has neither, so `created_at` becomes the clock start.

**`cook_events`** (`db/migrations/0010_cook_events.sql`) is written once, at the end of the whole finish flow (after the leftovers decision, whichever way it goes) — not incrementally — via `lib/api/cookEvents.ts`'s `createCookEvent`. `inventory_mutations`/`leftovers_created` store what was *actually applied* (post-user-edit), not the initial proposal. `fetchCookEvents` (History, `app/(tabs)/search.tsx`) joins to `recipes` with a second query rather than a PostgREST embedded select (`.select('*, recipes(title)')`) — see the Supabase typing gotcha above; every table's `Relationships: []` means embedded-select type inference isn't reliable here, so two simple queries joined in JS sidesteps it.

**Kitchen Check-In (Phase 5) is purely client-side — no new Edge Function, no new migration.** Every signal `lib/checkInScoring.ts`'s `scoreItem` uses (`verification_status`, `last_verified_at`, `expiry_estimated`/`expiry_user_provided`, `preparation_state`, `quantity_confidence`) already existed on `inventory_items`. It's the same "derive from already-loaded `items`, no query" pattern as `lib/rescueRow.ts` — deterministic, no LLM, most items score 0 and are filtered out entirely (`CHECK_IN_THRESHOLDS.minimumScore`). All five tuning knobs live in one exported `CHECK_IN_THRESHOLDS` const per spec's explicit instruction — retune there, not scattered through `scoreItem`. `determinePromptType` (existence / quantity / leftover) is a small standalone decision function, not hardcoded per item, so a new item shape only needs one new branch there.

**Check-In's mutations skip Phase 4's propose/confirm split on purpose.** `app/check-in.tsx` calls `lib/checkInResponses.ts`'s `applyCheckInResponse` directly on button tap — no review step, because tapping a response IS the confirmation (spec is explicit about this being a different trust model than Cooking Mode's finish flow). `applyCheckInResponse` still only ever calls `editItem`/`removeItem` (never a parallel write path), so the "does the LLM/does Check-In silently mutate inventory" audit (see Commands' grep) still holds — Check-In shows up as expected `editItem`/`removeItem` hits, gated by the user's own tap rather than a separate confirm screen, which is the correct exception, not a bug.

**Check-In sessions snapshot their batch once.** `app/check-in.tsx` does `useState(() => getCheckInBatch(items))` (lazy initializer, not `useMemo(..., [items])`) — deliberate, so responding to card 2 doesn't reshuffle or shrink the list the user is mid-way through. Resolved items still update `useInventory().items` immediately (so Rescue Row/Pantry/matching see the change right away); the *next* Check-In session just re-scores from scratch.

**"Gone"/"Discarded"/"Ate It" delete; everything else confirms in place.** Same pattern as Phase 4's cooking mutations (fully-consumed items are deleted, not soft-marked) — one consistent answer to "how does an item stop being active" across the app, not two competing ones. Don't add a new `consumed`/`archived` status enum value for this without a real reason; deletion already does the job and every downstream consumer (Rescue Row, recipe matching, `isUncertain`) already excludes deleted items for free since they all read `useInventory().items`.

**Cookbook is now a nested stack (Phase 6), same pattern as Pantry.** `app/(tabs)/cookbook/_layout.tsx` wraps its own `Stack` (`index`/`add`/`scan`/`scan-review`) in a new `CookbookScanContext` scoped to just that stack — mirrors `InventoryContext.quickAddDraft`'s draft-handoff pattern (context, not router params) but correctly scoped to a Cookbook-only concern rather than living in the app-wide `InventoryContext`. `cookbook/index.tsx` lists every recipe (`fetchUserRecipes`), supports a Favorites filter chip and a favorite-star toggle on `RecipeCard` (which gained an optional `style` override prop so it can be reused in a 2-column grid, not just Home's horizontal-scroll row).

**Cookbook Scan reuses Receipt Scan's infrastructure, per spec.** `lib/imageCapture.ts` was extracted from `lib/receiptScanner.ts` this phase (camera/photo-library picking + HEIC→JPEG normalization — Claude vision rejects HEIC); both `receiptScanner.ts` and the new `lib/cookbookScanner.ts` now call into it. Cookbook Scan also reuses the same private `receipts` Storage bucket (not a new one) under a `<user>/cookbook/` prefix — the bucket's RLS only checks the first path segment against the uploader's own user id, so a subfolder is enough to keep it distinct without a new migration. `supabase/functions/cookbook-scan/` extracts title/ingredients/instructions only (nothing else invented, per spec), runs ingredients through the same canonical-food matching every other pipeline uses, and computes a deterministic `needs_verification` flag server-side from confidence thresholds rather than trusting the model to self-report — see the orange "?" `UncertaintyBadge` on low-confidence ingredients and a whole-recipe banner in `cookbook/scan-review.tsx`.

**Nutrition is a real deterministic service, not an LLM guess (Phase 6).** `nutrition_data` (`db/migrations/0013_nutrition_data.sql`) seeds per-100g calories/protein/carbs/fat for every canonical food from USDA FoodData Central-informed figures (see README's Known limitations for what "informed by" means). `lib/nutritionCalculation.ts`'s `computeRecipeNutrition` (and its Deno port, `_shared/nutritionCalculation.ts`, kept in sync manually — same reasoning as `recipeMatching.ts`'s split) sums each ingredient's nutrition scaled by quantity, converting only real weight units (g/kg/oz/lb) to grams via fixed factors — count-ish units (cup, clove, can, ...) are excluded from the sum rather than guessed, and any unmatched-`canonical_food_id` ingredient is likewise excluded. Either case sets `is_partial: true` on the result so the UI states the estimate is partial instead of showing false precision. This runs server-side inside `_shared/recipeGeneration.ts`'s `requestRecipesFromModel` (so every generated recipe — Sous Chef and Home suggestions alike — always has `nutrition` populated before the dietary-violation retry loop even sees it) and client-side on manual/scanned saves (`cookbook/add.tsx`, `cookbook/scan-review.tsx`).

**Nutrition logging is consumption-triggered only — this is the load-bearing rule for Phase 6, same weight class as Phase 4's confirm-before-mutate rule.** Saving or generating a recipe computes and stores a per-serving `nutrition` estimate on the recipe itself, and that's it — it never writes to `daily_nutrition`. Only two call sites ever call `lib/api/dailyNutrition.ts`'s `logDailyNutrition`: `recipe/[id]/finish.tsx`'s `finalize()` (once `servings_consumed` is known, right before `createCookEvent`) and `lib/nutritionLogging.ts`'s `logLeftoverConsumption` (called from Pantry's new "I ate this" action and from Check-In's "Ate It" response, both on a `leftover`-state item). Verify this hasn't regressed with `grep -rn "logDailyNutrition" app/ lib/` — exactly those two call sites should show up; a new hit anywhere in recipe creation/generation is a bug. `logLeftoverConsumption` is a no-op (`{ logged: false }`) when the item has no `source_recipe_id` or that recipe has no computed `nutrition` — skipped, never fabricated as a "standalone" entry. Eating a leftover never creates a `cook_events` row (no new cooking happened); only Finish Cooking does that. `daily_nutrition` writes go through the `increment_daily_nutrition` Postgres function (`security definer` + an explicit `auth.uid()` guard, since `security definer` bypasses RLS) rather than a plain upsert, because "add this meal's macros to today's running total" can't be expressed as a PostgREST upsert (which replaces a row, not increments it).

**Macro rings (`components/MacroRingRow.tsx`) are static badges, not goal-based progress fills.** There's no calorie/macro target data model in scope this phase (no personalization requested), so a true percent-fill ring would either be meaningless or silently imply a target the app never set. `size="compact"` (Home, Section A, top of the screen) vs. `size="full"` (the Macros tab, `app/(tabs)/macros.tsx`, which also has simple day-back navigation via `lib/api/dailyNutrition.ts`'s `shiftLocalDate`) share the same component.

**Technique videos are a real YouTube Data API result behind an LLM query-picker, same shape as the nutrition/matching split (Phase 7).** `supabase/functions/recipe-videos/` does exactly two things, in order: `_shared/techniqueIdentification.ts` makes one small text-only Claude call to name the recipe's single most important/non-obvious technique (its only job — it never sees or produces video data), then `_shared/youtubeSearch.ts` makes a real `youtube.googleapis.com/youtube/v3/search` call against `"<technique> technique"` and maps the response 1:1 into `YoutubeVideoResult[]` — every field (`video_id`, `title`, `channel_title`, `thumbnail_url`, `published_at`) comes straight off the API response, nothing filled in or guessed. Like every other Edge Function here, it never writes to `recipes` — it returns `{ technique, search_query, retrieved_at, results }` and the client persists it.

**Video lookups are NOT eager at generation time — this is a deliberate quota decision, not an oversight.** The YouTube Data API's default free quota is small (10,000 units/day, 100 units per search call — effectively ~100 searches/day). `recipe-suggestions` generates 3-5 candidates per Home visit that are mostly never saved; eagerly searching for all of them would burn quota on content nobody chose. So: `_shared/recipePayload.ts`'s `buildRecipeSuggestionPayload` always sets `youtube_metadata: null` — neither `sous-chef-chat` nor `recipe-suggestions` ever calls `recipe-videos` server-side. Instead there are exactly two client-triggered fetch paths, both grep-able via `fetchRecipeVideos`: (1) `app/sous-chef.tsx` fetches client-side for the one recipe a chat turn actually generates, right after the reply renders (fire-and-forget, the chat card shows immediately and the video preview pops in once it resolves); (2) `app/recipe/[id].tsx` lazily fetches once per recipe, only when the loaded `recipe.youtube_metadata` is still `null`, then persists the result via `lib/api/recipes.ts`'s `updateRecipeYoutubeMetadata` so it's cached on `recipes.youtube_metadata` and never re-searched on subsequent views (a manual refresh button re-runs it unconditionally). Cooking Mode never fetches at all — by the time a user reaches Cooking Mode they've necessarily passed through the recipe detail screen first ("Cook This"), so `youtube_metadata` is already cached on the row `cook.tsx`'s own `fetchRecipeById` call reads.

**`recipes.youtube_metadata` needed no new migration.** The column existed since Phase 3's original schema (`db/migrations/0008_recipes.sql`, `youtube_metadata jsonb`) — it just sat untyped (`unknown | null`) until Phase 7 gave it a real shape (`RecipeYoutubeMetadata`, `types/recipe.ts`) and a writer. jsonb has no fixed Postgres-level structure anyway, so there was nothing to migrate.

**Cooking Mode's per-step technique match is a dumb keyword-overlap check, same philosophy as `lib/matchIngredientsToStep.ts`.** `lib/matchTechniqueToStep.ts`'s `stepMatchesTechnique` lowercases both the step text and the technique phrase, splits into words >3 characters, and checks for any overlap — not real NLP, "where applicable" per spec, not exhaustive. `components/TechniqueVideoSlot.tsx` uses the match result only to relabel ("This step: ..." vs. "Watch: ...") — the same cached videos render either way, and when nothing in the whole recipe cached (`youtube_metadata` still null, or the search returned zero results), the slot renders nothing rather than the old static "coming soon" placeholder.

**Settings (`app/settings.tsx`) is the ONLY write path to `user_preferences` (Phase 8).** `lib/api/userPreferences.ts`'s `updateUserPreferences` is called from exactly one place — verified by grep (see Commands). This matters specifically for `dietary_restrictions`: it's a hard constraint, and the one thing that must never be alterable by anything other than an explicit user edit. If you ever add a feature that "learns" a preference and writes it back to `user_preferences`, that's a bug for `dietary_restrictions`/`skill_level`/`equipment` — behavioral signal is only ever allowed to nudge a computed *score*, never the stored row (see the ranking paragraph below).

**Deterministic multi-signal recommendation ranking (Phase 8) — the load-bearing new piece, same weight class as Phase 4's confirm-before-mutate rule.** `supabase/functions/_shared/recommendationScoring.ts`'s `computeRecipeScore` is pure arithmetic over real data — pantry coverage, urgency-weighted rescue score (from `PantryContext.rescueEntries`, not just names), cuisine preference (explicit `cuisineWeights` nudged, never overwritten, by recent cook frequency — `MAX_BEHAVIORAL_PREFERENCE_NUDGE` bounds how far), a stated time limit if one exists (neutral 0.5 when none was asked, e.g. every Home suggestion), equipment owned vs. `recipe.equipment_needed`, and novelty/repetition from `PantryContext.recentCookEvents` (last 30 days) — never an LLM judgment call, so "why did this rank where it did" always has a concrete numeric answer (`RecipeScoreBreakdown`). `macro_match` is a documented constant 0.5: there's no stated macro/nutrition goal in `user_preferences` to compare against, and scoring it as anything else would be inventing a preference nobody stated. `_shared/recipePayload.ts`'s `buildRecipeSuggestionPayload` is the single choke point that calls this (same "one place, can't drift" pattern already used for nutrition/video wiring) — `recipe-suggestions/index.ts` sorts its four candidates by score; `sous-chef-chat/index.ts` computes one recipe's score for explainability (one candidate, nothing to sort).

**Ranking must never run before the dietary hard-filter, and both entry points now verify that defensively, not just structurally.** `generateRecipes` (Phase 3) already only returns dietary-compliant recipes — that's the real enforcement. Phase 8 adds a second, redundant `findDietaryViolations` check immediately before `buildRecipeSuggestionPayload` runs in both `recipe-suggestions/index.ts` and `sous-chef-chat/index.ts`'s `buildFinalRecipe` — this should never actually filter anything out (if it does, `console.error` fires, which would be a real bug to investigate), but ranking must never be the place a violation could slip through unverified. Two new Deno test files (`_shared/dietaryRestrictions.test.ts`, `_shared/recommendationScoring.test.ts`, runnable via `deno test` — see Commands) are this repo's only real automated tests, added specifically because this phase's spec asked to "add a test/check if reasonable" and Deno's built-in runner made that cheap for exactly the pure-function modules that matter most here.

**`why_bullets` replaces trusting LLM prose for explainability, with a fallback for what came before.** `buildWhyBullets` (`_shared/recommendationScoring.ts`) generates plain-string bullets straight from the score breakdown's real numbers — never narrated by the model. `RecipeCard`'s full variant and `app/recipe/[id].tsx` render `why_bullets` when non-empty, falling back to the old free-text `why_this_works` otherwise (recipes saved before Phase 8, or manual/scanned recipes, which never go through scoring at all — `equipment_needed`/`why_bullets`/`score`/`score_breakdown` are just empty/null defaults for those source types, not errors).

**Behavioral signal collection is two new insert-only tables plus pure derivation functions — not a general analytics system.** `item_dispositions` (Phase 8) logs *why* an inventory item left the pantry (consumed/discarded/unknown), written only from Check-In's Gone/Ate It/Discarded responses and Pantry's "I ate this" — never from a plain delete or a cooking mutation, both of which have ambiguous-or-already-tracked provenance (see `db/migrations/0016`'s header comment). `recommendation_events` logs Home suggestions shown vs. saved (`app/(tabs)/index.tsx`), the one signal that can't be derived from any existing table. `lib/behavioralSignals.ts` has pure functions for all six signals the product spec's section 1 calls out, but **only two are actually wired into the score** — cuisine cook frequency (`preference_match`'s nudge) and recent cook history broadly (`novelty_score`/`recent_meal_repetition_penalty`) — because the product spec's own scoring formula (section 3) doesn't name the other four as score terms. Don't assume `dispositionRatesByFood`/`recipesSavedNotCooked`/`averageCookTimeMinutes`/`suggestionSkipRatesByCuisine` are dead code if you don't see them called from the scoring path — they're real, correct, and intentionally not force-fit into a formula that doesn't ask for them; a future phase can wire any of them in without new data collection.

## Gotchas

- `.npmrc` sets `legacy-peer-deps=true`. Without it, `npm install` fails: `expo-router`'s `@expo/metro-runtime` pulls in `react-dom@19.3.0`, which wants a newer React than `expo@57.0.23` pins — an upstream SDK 57 mismatch, not something in this repo's control.
- `react-dom` / `react-native-web` are installed only so `expo export --platform web` works as a bundling smoke test in environments without a simulator/device. Not part of the product requirements.
- Dates (purchased/opened/expiry) are plain `YYYY-MM-DD` text fields (`lib/dateInput.ts`), not a native date picker — a deliberate Phase 1 scope cut.
- `supabase/functions/` is Deno, not Node — it's excluded from the root `tsconfig.json` (`exclude: ["supabase/functions"]`) so `npx tsc --noEmit` doesn't choke on `Deno.env`/`npm:`/`jsr:` syntax. Typecheck Edge Functions separately with `deno check` (see Commands) from *inside* `supabase/functions/` — there's a `deno.json` there specifically so Deno doesn't climb up and get confused by the app's root `package.json`/node_modules. Don't run `deno check --all`: it deep-checks `@supabase/auth-js`'s WebAuthn `.d.ts` files against browser-only DOM lib types Deno doesn't have, which fails even though nothing in this codebase touches that code path. Plain `deno check <file>` is the correct signal.
- The Edge Functions never write to `inventory_items` or `recipes` — if you're tempted to have any of the four insert directly, don't; that breaks the "LLM never silently writes" rule. Suggestions only; the client writes only after the user acts (confirming a Quick Add/Receipt Scan batch, or tapping a recipe card).
- `_shared/recipeGeneration.ts` and `_shared/pantryContext.ts` intentionally read `inventory_items`/`canonical_foods`/`user_preferences` loosely typed (`Record<string, unknown>` / ad hoc casts), not through the app's `Database` generic — consistent with the rest of `supabase/functions/`'s deliberate avoidance of cross-runtime imports from `types/`. Don't try to "fix" this by importing `types/database.ts` into Deno code.
- The Search tab (`app/(tabs)/search.tsx`) currently renders cook History, not search — a deliberate Phase 4 placeholder-with-real-data (see Project phase). Don't assume the file name/tab label reflects what's actually implemented there.
- `finish.tsx` is a four-stage local state machine (`'loading' | 'servings' | 'mutations' | 'leftovers' | 'saving'`) in one file, not four screens — resist splitting it into separate routes unless there's a real navigation reason (e.g. deep-linking to one stage), since the stages share mutable state (`mutations`, `appliedMutations`) that would otherwise need to round-trip through router params.
- Check-In's staleness scoring and Cooking Mode's state-mode mutation step-down (Phase 4) both traverse the same `QuantityState` progression (`full → mostly_full → half → low → almost_empty`) but are independent, un-shared logic — `lib/checkInScoring.ts` doesn't call into `lib/cookingMutations.ts` or vice versa. Not a bug; "how stale before flagging" and "how far to step down when cooked" are genuinely different questions. Don't reflexively merge them if you touch one.
- **`Database['Functions']` can't use the `Record<string, never>` empty-schema shortcut the way `Views`/`Enums`/`CompositeTypes` do.** `@supabase/supabase-js` resolves any `.rpc('fn', {...})` call's params type to `undefined` when `Functions` is typed that way, producing `Argument of type '{...}' is not assignable to parameter of type 'undefined'` even though the call is correct at runtime. Fix: give the specific function a real `{ Args: {...}; Returns: T }` entry in `Functions` (see `increment_daily_nutrition` in `types/database.ts`). Discovered wiring up Phase 6's daily-nutrition RPC; if you add a new Postgres function called via `.rpc()`, it needs this same treatment, not the shortcut.
- `supabase/functions/` is six functions as of Phase 7 (`quick-add-parse`, `receipt-scan`, `sous-chef-chat`, `recipe-suggestions`, `cookbook-scan`, `recipe-videos`) — update this count if you add a seventh, it's referenced from README's Setup instructions too.
- The YouTube Data API's default free quota is small (~100 searches/day, 100 units per `search.list` call against a 10,000/day budget) — don't add a new eager-fetch call site for `recipe-videos` without checking the quota reasoning in this file's Phase 7 Architecture paragraphs first. Grep `fetchRecipeVideos` call sites (should be exactly two: `app/sous-chef.tsx`, `app/recipe/[id].tsx`) before assuming it's safe to call from a new screen.
- `supabase/functions/_shared/*.test.ts` files are real `deno test`-runnable tests, not dead code and not part of any deployed function bundle (Supabase only deploys what an `index.ts` actually imports, and no `index.ts` imports a `.test.ts` file). If you add a new pure-function module in `_shared/` with a real invariant worth pinning down (especially anything touching the dietary hard-filter or the scoring formula), consider adding a sibling `.test.ts` rather than assuming this repo has "no tests" — it has exactly two files' worth, and that pattern is meant to be extended, not treated as a one-off.
- `recommendationScoring.ts`'s weights (`WEIGHTS` const) and thresholds (`MAX_BEHAVIORAL_PREFERENCE_NUDGE`, `REPETITION_FULL_PENALTY_DAYS`, `REPETITION_HALF_PENALTY_DAYS`, `NOVELTY_FULL_CREDIT_DAYS`) are reasoned-through defaults reflecting the product spec's stated priority order, not tuned against real usage (no device/CLI in this environment to observe real cooking patterns against). Retune them directly in that file — the formula's shape and the tests' property-based assertions (not exact-number assertions) were written specifically so retuning doesn't require touching test expectations.

## Conventions

Git commits in this repo currently use a `phase N: ` subject prefix (lowercase, e.g. `phase 3: add recipe data model and rls policies`) with multiple focused commits per phase rather than one large one — this was introduced for Phase 3's task and appears intended to continue for later phases; check with the user if a task doesn't specify.

## Project phase

This is Phase 8 of an 8-phase build — the final phase in the original MVP sequence (see PLAN.md locally if present — it's gitignored, not in the repo). Phase 1 shipped project skeleton, auth, the canonical food model, and inventory CRUD. Phase 2 added real (LLM-backed) normalization, receipt scanning, deterministic expiry, verification handling, and the Rescue Row. Phase 3 added Sous Chef, recipe generation, recipe-to-inventory matching, and Home's "What should I cook?" section. Phase 4 closed the core loop — Cooking Mode, the confirm-before-mutate inventory deduction flow, leftovers, and cook History — the first phase where Capture → Understand → Rescue → Decide → Cook → Reconcile worked end to end. Phase 5 added Kitchen Check-In — the "Reconcile" step's counterpart for pantry drift that *isn't* caused by cooking: deterministic staleness scoring, a capped tap-through card flow, and Home's `KitchenStatusRow`/`CheckInBanner`. Phase 6 built out Cookbook for real and added a deterministic nutrition service plus consumption-triggered macro logging. Phase 7 wired in live YouTube technique-video search. Phase 8 (current) closes the loop back onto every earlier phase's data: a real Settings screen for cuisine/dietary/equipment preferences, and a deterministic multi-signal ranking function (see the material above) that uses pantry coverage, rescue urgency, cuisine preference, stated time limits, equipment, and cook history to rank Home's suggestions and Sous Chef's recipe — never an opaque LLM ordering, and dietary restrictions remain a hard pre-filter no amount of "learning" can touch. Not built yet: a real shopping list (`create_shopping_items` is still a stub), Global Search (Search tab still shows cook History — see the Search-tab gotcha above), or any of the explicit Phase 8 non-goals (social feed, marketplace, grocery delivery, restaurant recommendations, budgeting, smart-appliance integrations, fully autonomous inventory management, household sharing) — those are all out of the original 8-phase MVP scope entirely, not deferred to a numbered future phase. Every tab and every core loop step (Capture → Understand → Rescue → Decide → Cook → Reconcile) is fully functional — `components/ComingSoon.tsx` has no remaining callers as of Phase 6, though it's left in place in case a future phase needs a placeholder again.
