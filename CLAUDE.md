## Commands

```sh
npm install              # requires .npmrc's legacy-peer-deps=true (see Gotchas)
npm start                # expo start — press i/a/w for iOS/Android/web
npm run ios / android / web
npx tsc --noEmit          # typecheck the app (excludes supabase/functions — see Gotchas)
npx expo-doctor           # validate SDK/config/dependency health
npx expo export --platform web   # bundle-only smoke test; useful when no simulator is available
cd supabase/functions && deno check <fn>/index.ts   # typecheck one Edge Function (needs `brew install deno`)
supabase functions deploy quick-add-parse   # deploy an Edge Function (needs `supabase link` first)
                                             # others: receipt-scan, sous-chef-chat, recipe-suggestions
supabase secrets set ANTHROPIC_API_KEY=...  # required by all four Edge Functions, never a client env var
grep -rn "editItem\|removeItem\|addItem(" app/ lib/ supabase/functions/ --include="*.ts*" | grep -v InventoryContext.tsx
                                             # the "does anything touch inventory it shouldn't" audit —
                                             # see Gotchas; re-run after touching recipe/cooking code
```

Env vars: copy `.env.example` to `.env` and fill in a Supabase project's URL/anon key (`EXPO_PUBLIC_`-prefixed, inlined by Metro at build time — see `lib/supabase.ts`, which throws at import time if they're missing). The Anthropic key is a **Supabase secret**, not an app env var — it's only ever read inside `supabase/functions/*/index.ts` (Deno), never bundled into the client.

Database: schema lives only in `db/migrations/*.sql`, applied in filename order via the Supabase SQL Editor (or `supabase db push` with the CLI). There is no ORM — the Supabase dashboard is never the source of truth; if the schema changes, write a new numbered migration and update `types/database.ts` to match.

## Architecture

**Routing (expo-router, file-based):** `app/_layout.tsx` wraps the whole tree in `AuthProvider` > `InventoryProvider` (moved to the root in Phase 3 so `sous-chef.tsx` and `recipe/[id].tsx` — both outside `(tabs)` — can read inventory too; it's a no-op until there's a session) and mounts a root `Stack` with six screens: `(auth)`, `(tabs)`, `sous-chef` (modal), `recipe/[id]`, `recipe/[id]/cook`, `recipe/[id]/finish`. Route groups don't add URL segments, so exactly one `index.tsx` across `(auth)`/`(tabs)` may claim `/` — `(tabs)/index.tsx` owns it; `(auth)` has no `index.tsx` on purpose (see git history for why: both groups having an index route collides on `/`). The auth gate isn't a redirect at the root — each group's own `_layout.tsx` checks `useAuth().session` and calls `<Redirect>` to the other group. `(tabs)/pantry/` is its own nested `Stack` (list → add → `[id]` edit → quick-add → receipt-scan → quick-add-review, the last shared by both add flows). `app/recipe/[id].tsx` (a file) and `app/recipe/[id]/` (a directory holding `cook.tsx`/`finish.tsx`) coexist fine as siblings under the same dynamic segment name — verified via `expo export --platform web`, no route-conflict error.

**State:** two React contexts, not a global store. `lib/auth/AuthContext.tsx` wraps Supabase auth session state. `lib/inventory/InventoryContext.tsx` wraps inventory items, canonical foods, and `food_storage_rules` for the whole authenticated app, and also carries `quickAddDraft` — the parsed-but-unsaved batch from either Quick Add or Receipt Scan (each `QuickAddDraftItem` carries its own `source`) — so the two entry screens → `quick-add-review.tsx` handoff doesn't need to serialize items through router params.

**Supabase typing gotcha:** `types/database.ts`'s `Database` type must use `type X = {...}` (type aliases), never `interface X {...}`, for every `Row`/`Insert`/`Update` shape. `@supabase/supabase-js`'s generics require each table to structurally satisfy `Record<string, unknown>`-style index signatures, and TypeScript only allows that implicit match for type aliases, not named interfaces — using an interface silently degrades every `.from(...)` call to `never`. Each table also needs a `Relationships: []` field and the schema needs `Views`/`Functions`/`Enums`/`CompositeTypes`, matching what `supabase gen types typescript` would produce.

**Quick Add / Receipt Scan normalization pipeline (Phase 2):** `lib/quickAddParser.ts` no longer parses anything itself — it calls the `quick-add-parse` Edge Function (`supabase/functions/quick-add-parse/`) and maps the response. `lib/receiptScanner.ts` does the same via `receipt-scan`, after normalizing the photo to JPEG (`expo-image-manipulator` — Claude's vision API rejects HEIC, the iOS camera default) and uploading it to the private `receipts` Storage bucket. Both Edge Functions share one normalization contract in `supabase/functions/_shared/matching.ts` (the canonical-foods prompt fragment + JSON response validator) — that shared module, not a literal two-call pipeline, is what "reuse the normalization pipeline" means here; each function still makes just one Claude call. Neither function ever writes to `inventory_items` — both only return suggestions, and every result still lands on `quick-add-review.tsx` before saving. `lib/functionsError.ts` unwraps the real error message from a `FunctionsHttpError`, shared by both client modules.

**Deterministic expiry (Phase 2, no LLM):** `db/migrations/0006_expiry_estimation.sql` installs a Postgres trigger that looks up `food_storage_rules` (seeded in `0005_food_storage_rules.sql`, keyed by `canonical_food_id` + `preparation_state` + `storage_location` + `is_opened`) and sets `expiry_estimated` whenever those fields or `purchased_at`/`opened_at` change. No match (unresolved `canonical_food_id`, or a combination with no seeded rule) means `expiry_estimated` stays null — never a guessed number. The client mirrors this same lookup in `lib/foodStorageRules.ts`'s `findStorageRule` to read `is_safety_critical` for display tone (see the edit screen). `lib/formatInventory.ts`'s `getEffectiveExpiry` prefers `expiry_user_provided` over `expiry_estimated`.

**Uncertainty rule (cross-cutting):** any inventory data not confirmed by the user must be visually distinguishable everywhere it's shown. This is enforced by a single component, `components/UncertaintyBadge.tsx`, rendered whenever `verification_status` is `ai_estimated` or `needs_verification` (see `lib/formatInventory.ts`'s `isUncertain`). Don't build a second/parallel way to flag uncertain data — route new cases through this component and status field. Saving from the edit screen, or tapping a row's quick-verify checkmark (`InventoryItemRow`'s `onVerify`), is what clears it — both set `verification_status: 'confirmed'` and `last_verified_at`.

**Rescue Row (Phase 2):** `lib/rescueRow.ts`'s `getRescueRowEntries` is a pure function over already-loaded `items` — no query, no LLM. It classifies each item by at most one reason (expiring > leftover > low quantity, in that priority order) and sorts soonest-first. Keep it that way — this is explicitly "what needs attention," not recommendation logic.

**Recipe-to-inventory matching (Phase 3):** `lib/recipeMatching.ts`'s `matchRecipeToInventory`/`matchIngredient` is the deterministic, non-LLM classifier (Already Have / Verify / Missing) reused everywhere a recipe renders — `RecipeCard`, the recipe detail screen, and both server-side generation paths. It has an independent Deno port at `supabase/functions/_shared/recipeMatching.ts` (same algorithm, same unit-synonym table as `lib/quickAddParser.ts`'s `UNIT_WORDS`, kept in sync manually — there's no cross-runtime import here, same reasoning as the Supabase-client duplication below). The recipe detail screen (`app/recipe/[id].tsx`) deliberately re-runs this live against current `useInventory().items` rather than trusting `recipes.ingredients[].inventory_match`, which is only a point-in-time snapshot for explainability.

**Sous Chef & recipe generation (Phase 3):** `supabase/functions/sous-chef-chat/` runs a real manual Claude tool-calling loop (six tools: `get_inventory`, `get_rescue_items`, `get_user_preferences`, `generate_recipe`, `match_recipe_to_inventory`, `create_shopping_items` — a no-op stub) — the model decides when to call what; it never fabricates inventory data because every fact it uses comes back from a real tool call. Each chat turn is stateless: the client (`app/sous-chef.tsx` via `lib/sousChef.ts`) resends the full text-only history, and the server re-gathers fresh context every turn rather than replaying old tool_use/tool_result blocks. `supabase/functions/recipe-suggestions/` is the non-conversational sibling for Home's suggestions — same generation/matching pipeline, invoked directly instead of via a tool loop. Both share `_shared/recipeGeneration.ts` (one Claude call per generation batch — extraction and canonical-food matching happen together in one prompt, same "shared module over literal two-call pipeline" design as Phase 2's normalization) and `_shared/recipePayload.ts` (shapes a generated+matched recipe into the wire format both entry points return, so the client's `RecipeCard` never sees two different shapes).

**Dietary restrictions are a hard constraint, structurally enforced — not just prompted.** `_shared/dietaryRestrictions.ts`'s `findDietaryViolations` runs a keyword check against every candidate recipe's ingredient names; `generateRecipes` in `_shared/recipeGeneration.ts` discards any violating recipe and regenerates (up to 3 attempts) before anything reaches the client. If you touch recipe generation, do not remove or bypass this check even if it seems redundant with the system prompt — the system prompt is the soft layer, this is the hard one. The keyword list is a curated common set (vegetarian/vegan/pescatarian/gluten-free/dairy-free/nut-free/shellfish-free/egg-free), not exhaustive — see README's Known limitations before treating it as a real allergen safety system.

**Recipes persist, and now they cook (Phase 4).** `recipes` (`db/migrations/0008_recipes.sql`) stores what's generated; tapping a `RecipeCard` (in chat or on Home) saves it via `lib/api/recipes.ts`'s `suggestionToRecipeInsert` + `createRecipe`, then navigates to `recipe/[id].tsx`. Its "Cook This" button pushes `recipe/[id]/cook` (step-by-step, per-step timers via `lib/parseStepDuration.ts`'s regex, inline ingredients via `lib/matchIngredientsToStep.ts`'s substring match, a `TechniqueVideoSlot` placeholder for Phase 7). "Finish Cooking" from any step pushes `recipe/[id]/finish`.

**The confirm-before-mutate rule is the load-bearing one for Phase 4 (and the whole app's trust model).** `recipe/[id]/finish.tsx` is the *only* place recipe-related code writes to `inventory_items` — verified by grepping every `editItem`/`removeItem`/`addItem` call site (see Commands) and confirming the only hits outside Pantry's own pre-existing CRUD screens are inside `finish.tsx`, gated behind the user's "Update Pantry" tap. `lib/cookingMutations.ts`'s `proposeInventoryMutations` is deterministic (no LLM) and only *proposes* — it returns editable `ProposedMutation[]`, it never calls `editItem`/`removeItem` itself. Re-run that grep after touching anything recipe- or cooking-related; a new hit outside `finish.tsx` (behind confirmation) or Pantry is a bug, not a feature.

**Mutation modes (`lib/cookingMutations.ts`):** `'quantity'` (both the recipe ingredient and a matched item have a numeric quantity in a comparable unit — reuses `lib/recipeMatching.ts`'s exported `normalizeUnit`) scales the deduction by `servingsPrepared / recipe.servings` and spreads it across matched items in order; fully-consumed precise quantities are removed (`removeItem`), not left at zero. `'state'` (only an approximate `quantity_state` match) steps down one level via a fixed `STATE_STEP_DOWN` map, floored at `almost_empty` — never auto-removed, per spec's "leave it at Almost Empty" default. An ingredient with no canonical match, or a match with neither a comparable quantity nor a `quantity_state`, produces no proposal at all — there's nothing responsible to change automatically.

**Leftovers close the loop back into Rescue Row.** Confirming the leftovers prompt in `finish.tsx` calls `addItem` with `preparation_state: 'leftover'`, `source: 'cooking'` (a value added to the `inventory_source` enum in its own migration, `0011_inventory_source_cooking.sql` — Postgres won't let a new enum value be used in the same transaction that adds it), `storage_location: 'fridge'`, `verification_status: 'confirmed'` (the user just made it, no uncertainty). No changes needed to `lib/rescueRow.ts` — it already ages any `leftover` item by `opened_at ?? created_at`, and a freshly created leftover naturally has neither, so `created_at` becomes the clock start.

**`cook_events`** (`db/migrations/0010_cook_events.sql`) is written once, at the end of the whole finish flow (after the leftovers decision, whichever way it goes) — not incrementally — via `lib/api/cookEvents.ts`'s `createCookEvent`. `inventory_mutations`/`leftovers_created` store what was *actually applied* (post-user-edit), not the initial proposal. `fetchCookEvents` (History, `app/(tabs)/search.tsx`) joins to `recipes` with a second query rather than a PostgREST embedded select (`.select('*, recipes(title)')`) — see the Supabase typing gotcha above; every table's `Relationships: []` means embedded-select type inference isn't reliable here, so two simple queries joined in JS sidesteps it.

## Gotchas

- `.npmrc` sets `legacy-peer-deps=true`. Without it, `npm install` fails: `expo-router`'s `@expo/metro-runtime` pulls in `react-dom@19.3.0`, which wants a newer React than `expo@57.0.23` pins — an upstream SDK 57 mismatch, not something in this repo's control.
- `react-dom` / `react-native-web` are installed only so `expo export --platform web` works as a bundling smoke test in environments without a simulator/device. Not part of the product requirements.
- Dates (purchased/opened/expiry) are plain `YYYY-MM-DD` text fields (`lib/dateInput.ts`), not a native date picker — a deliberate Phase 1 scope cut.
- `supabase/functions/` is Deno, not Node — it's excluded from the root `tsconfig.json` (`exclude: ["supabase/functions"]`) so `npx tsc --noEmit` doesn't choke on `Deno.env`/`npm:`/`jsr:` syntax. Typecheck Edge Functions separately with `deno check` (see Commands) from *inside* `supabase/functions/` — there's a `deno.json` there specifically so Deno doesn't climb up and get confused by the app's root `package.json`/node_modules. Don't run `deno check --all`: it deep-checks `@supabase/auth-js`'s WebAuthn `.d.ts` files against browser-only DOM lib types Deno doesn't have, which fails even though nothing in this codebase touches that code path. Plain `deno check <file>` is the correct signal.
- The Edge Functions never write to `inventory_items` or `recipes` — if you're tempted to have any of the four insert directly, don't; that breaks the "LLM never silently writes" rule. Suggestions only; the client writes only after the user acts (confirming a Quick Add/Receipt Scan batch, or tapping a recipe card).
- `_shared/recipeGeneration.ts` and `_shared/pantryContext.ts` intentionally read `inventory_items`/`canonical_foods`/`user_preferences` loosely typed (`Record<string, unknown>` / ad hoc casts), not through the app's `Database` generic — consistent with the rest of `supabase/functions/`'s deliberate avoidance of cross-runtime imports from `types/`. Don't try to "fix" this by importing `types/database.ts` into Deno code.
- The Search tab (`app/(tabs)/search.tsx`) currently renders cook History, not search — a deliberate Phase 4 placeholder-with-real-data (see Project phase). Don't assume the file name/tab label reflects what's actually implemented there.
- `finish.tsx` is a four-stage local state machine (`'loading' | 'servings' | 'mutations' | 'leftovers' | 'saving'`) in one file, not four screens — resist splitting it into separate routes unless there's a real navigation reason (e.g. deep-linking to one stage), since the stages share mutable state (`mutations`, `appliedMutations`) that would otherwise need to round-trip through router params.

## Conventions

Git commits in this repo currently use a `phase N: ` subject prefix (lowercase, e.g. `phase 3: add recipe data model and rls policies`) with multiple focused commits per phase rather than one large one — this was introduced for Phase 3's task and appears intended to continue for later phases; check with the user if a task doesn't specify.

## Project phase

This is Phase 4 of an 8-phase build (see PLAN.md locally if present — it's gitignored, not in the repo). Phase 1 shipped project skeleton, auth, the canonical food model, and inventory CRUD. Phase 2 added real (LLM-backed) normalization, receipt scanning, deterministic expiry, verification handling, and the Rescue Row. Phase 3 added Sous Chef, recipe generation, recipe-to-inventory matching, and Home's "What should I cook?" section. Phase 4 (current) closes the core loop — Cooking Mode, the confirm-before-mutate inventory deduction flow, leftovers, and cook History (see the material above) — this is the first phase where Capture → Understand → Rescue → Decide → Cook → Reconcile works end to end. Not built yet: Kitchen Check-In, nutrition/macro logging, real YouTube technique videos, a real shopping list (`create_shopping_items` is still a stub), or Cookbook/Macros beyond their placeholders. Home, Pantry, and now cooking (Sous Chef, recipe detail, Cooking Mode, Finish Cooking, History-in-Search) are fully functional; Cookbook and Macros are still `ComingSoon` placeholders (`components/ComingSoon.tsx`) — don't build features into them without new requirements from the user.
